# xhs-digest 图片笔记理解方案（实测）

> **定位**：把《xhs-digest 设计方案》§2 里「图文笔记」那一行（"正文全文 + 图片（图卡类必读；纯风景照快速扫）+ 评论"）展开成与视频管线同级的一套读法。
> **实测样本**：`notes/696117b2000000001a01e6ef/`（《九寨沟一日游轻徒步攻略🏃🏼‍♀️》，19 个图片文件 / 592 字正文 / 118 评论 / 2026-01-09 发布）。
> **合规前提**：全程只用已下载到本地的内容（note.json / comments.json / images/），未打开浏览器、未取任何外部信息。

---

## 1. 结论速览

| # | 结论 | 依据 |
|---|---|---|
| 1 | **读图的第一判据是"这张图对我的问题有没有增量"，不是"正文有没有提到它"** | 见 §3.1 的反例 |
| 2 | **纯风景照即使被正文点名，也不读**——正文文字已经覆盖了它的信息 | 正文点名"图15"只是说"我拍了树正群海"，信息在文字里，图里没有增量 |
| 3 | **真正值得读的是"信息在图上"的图，而这类图正文常常根本不提** → 必须有一次全图探查 | 002 是带距离/海拔/上下车站标注的导览图，正文只字未提 |
| 4 | **拼一张小图就是那次探查**：一次 ~4.6 k，替代逐张原图读（~38 k） | 2400×1440 的拼图上，一眼分出"哪一格是图卡、哪一格是风景" |
| 5 | 顺序固定为：**正文 → 拼图探查 → 定点原图 → 选择性看评论** | 见 §2 |

第 4 条是全部成本的所在：**省 token 的办法不是找更便宜的读图工具，而是不要逐张读原图**。拼图先用一张低清总览替代 19 次原图调用，把"读几张"从 19 压到 1。

## 2. 读法管线（四步）

### 第 1 步：正文先行

**只读 `note.json` 的正文**，在此之前别碰同目录的其它文件。正文产出两样东西：

**① 问题相关的线索**（本样本：14 步走法、进沟出沟时间、徒步段落、票务）——这部分是阶段 0 的主答案来源，往往已经占全篇信息量的大头；

**② 对图的处置判据**——逐条看正文怎么描述每张图：

| 正文对图的描述 | 处置 | 本样本实例 |
|---|---|---|
| 只说"拍了/看了 X"（风景照） | **不读**。文字已覆盖，图无增量 | "跑到一个栈道上去拍了树正群海（图15）" → 树正群海是风景照，**不看** |
| 说"图上标了/画了/列了/写了…"（信息在图上） | **必读**，且此时才需要解决"图N 对应哪个文件" | 本样本没有这类 |
| 完全没提 | **交给第 2 步的探查决定** | 002 导览图 |

**"正文点名"不等于"值得读"**，这两件事在上一版方案里被我混为一谈了：如果正文已经把该图的内容用文字说完了，读它花的是纯冗余 token。反过来，"值得读"也完全不依赖正文点名——见第 2 步。

### 第 2 步：拼图探查

把全部图片拼成一张低分辨率总览（480 px/格，角标编号），**自己作为多模态模型看一遍**。

```bash
python3 -I sheet.py <notes/<noteId>/images> /tmp/contact.jpg   # PIL，480 px/格
```

这一步同时完成三件事：

1. **找出"信息在图上"的图**（图卡、地图、表格、行程单、带批注的示意图）——不依赖正文是否提到；
2. **确认正文点名图的实际内容**——如果第 1 步判了"必读"，在这里对照一下哪一格是它；
3. **给配图选片**——美照素材在拼图分辨率下就能挑，**选片是"选"不是"读"，不必再开原图**。

**分辨率与成本的取舍**：拼图不是越小越好。分得清"这格是不是图卡、画的是什么景"即可，480 px/格 在 19 张的规模上够用。但要给单张拼图设上限（约 2400×1600 ≈ 5 k token 量级），图多就拆成几张拼图——**别让拼图本身涨成"又读了一遍原图"**。

### 第 3 步：定点原图

只把第 2 步挑出来的图送原图读。本样本只挑了 1 张（002 导览图，~2 k）。

读图用多模态模型直接看，**OCR 文本不能代替**：OCR 给的是没有位置关系的散词，而图上真正有信息量的恰恰是"距离数字挨着哪个站名""哪个站标了「下」"这类版式关系。本机的本地 OCR 能力另见《图片OCR实现方案》——那是一个可选的备用手段，**本方案的分流由第 2 步承担、阅读由多模态模型承担，不经过 OCR**。

### 第 4 步：选择性看评论

**排在精读之后**。先看评论会带着别人的注意力去读正文，反而漏掉正文自身的结构。读的时候只摘两类：

- **与当前问题相关的**（本样本：观光车 90 元不限次、站点上下车规则、冬季右线只到箭竹海、步行 2–3 万步、9:30 前进沟）；
- **与当前问题有影响的**（本样本：评论质疑"不是每个站点都能上下车"而作者没答；作者自述没看到犀牛海／老虎海）——**这类直接写进 §3 缺口**（输出模板不设"存疑"节，见 §4）。

其余（"好详细""wap"）直接略过。

### 与视频管线的对照

| | 定位信息在哪 | 探查手段 | 压缩比 |
|---|---|---|---|
| 视频（450 s 口播） | 时间轴上 | 形态判别 → 字幕带粗扫 → ASR 元话语定位回捞 | 全片 → 13 张长图 |
| 图片（19 张） | **没有时间轴，只有"哪一张"** | 正文判据 → 拼图探查 → 定点原图 | 19 张 → 1 张 |

两条管线同一个思想：**先花很小的代价把"哪里可能有信息"定位出来，再花视觉 token**。图片笔记的有利之处在于探查这一步可以一次做完。

## 3. 实测：判断过程与花销

### 3.1 反例：一个不该解的问题

正文写"跑到一个栈道上去拍了树正群海（**图15**）"。我按"正文点名 → 必读"去做了，于是：

1. 读下载序号 015 → 是一幅结冰的幕状瀑布，不是树正群海；
2. 反推编号规则，定位到 `016`（栈道俯瞰的梯级海子），确认"图15 = 016"；
3. 为了验证导览图上的路线序号是否真存在，又做了放大重跑 OCR、色彩通道分离、裁切核验。

**这三步全是无用功，约 5.4 k token。** 因为"树正群海"按阶段 0 的问题是**风景照**——正文已经说清了它在哪、怎么拍（"跑到一个栈道上去"），图片本身对"有哪些路线方案、这个季节怎么样、要多久"没有任何增量。**该图的价值判据在第 1 步就足以否决，根本不该进入定位环节。**

留作记录："图N"的编号在确实需要定位时**不能直接当序号用**（本样本实测偏移 +1，且偏移量不可外推）。但这是"信息在图上"那类图才需要处理的子问题，不是通用步骤。

### 3.2 正例：探查捞回了全篇最有价值的图

`002.webp` 是《九寨沟简易导览图》，正文只字未提，却含：

- **站点级距离**：1050 / 3000 / 8300 / 730 / 2050 / 1300 / 400 / 2300 / 1782 / 500 / 825 / 3155 / 1150 / 1200 / 100 / 2500 / 100 / 5800 m；
- **三条沟的长度**：则查洼沟 18 km、日则沟 17 km、树正沟 14 km；
- **海拔**：长海 3010 m、原始森林 2900 m；
- **每个站点标注的「上」／「下」**——这直接回答了评论区一个**作者自己没答清**的问题（站点是否都能随意上下车）；
- 橙色描白数字圈（裁切确认存在 1/9/11/12/14 等），与正文 14 步走法逐段吻合。

**这张图是拼图探查捞回来的，不是正文指过来的。** 反过来也说明：只按正文指引读图，本篇最有价值的一张会被整篇漏掉。

### 3.3 花销对照

| | 读图 | 文本 | 合计 |
|---|---|---|---|
| 朴素做法：19 张逐张读原图 | ≈ 38 k | note.json 0.9 k + comments 3.7 k | ≈ 42.6 k |
| **本方案（正确跑法）** | **≈ 6.7 k**（拼图 4.6 k + 002 原图 2.07 k） | 同上 | **≈ 11.3 k** |
| 本次实际 | ≈ 12.1 k（含 3.1 的 5.4 k 无用功） | + 误读 `downloads.json` 4.2 k | ≈ 20.9 k |

**读图省 82 %，总量省 73 %。**

## 4. 输出模板（图片笔记版）

**三节，不增不减**：

```text
# 笔记整理：<标题>
[溯源表：noteId / 作者 / 发布时间 / 互动数据 / 形态与图数 / 读图情况
        / 采集完整度 / 本地目录 / 原链接 / 整理目的]

## 1. 与当前问题相关的总结     ← 直接回答，放最前；按问到的维度分小段写全
   整体路线（有序走法 / 覆盖范围 / 换乘机制）
   打卡机位 ｜ 时间与时段 ｜ 注意事项（取舍） ｜ 时效错位 …
## 2. 结构化提炼              ← 11 维度全填，无信息标"未提及"；末尾附图卡索引
## 3. 待进一步确认的缺口       ← 只列与本次问题相关或会影响决策的，按问题分组
```

四条约定：

- **§1 要写全、不能只给要点摘要**：问到的每个维度都要成段写出**结论本体**，而不是"有这个维度"的提示。实测第一次交付时 §1 只写了"一日游可覆盖的景点范围：右线(…)＋左线(…)"这种**覆盖清单**，漏了三样必需的东西——**路线本身**（有序走法）、**打卡机位**、**时间与时段**，以及注意事项里的取舍项。判据：读者只读 §1 就应该能回答本次问题；
- **§2 是给后续问题用的可复用资产**：11 个维度（路线／打卡点／时间与时段／吃／住／穿衣／天气／路况／停车／购票／注意事项）**无论本次问不问都要填**，无信息也保留"未提及"——目的是**后续其他问题直接取用提炼好的，不必重读笔记**。所以"吃／住／停车未提及"留在 §2，**不进 §3**；
- **§3 按本次问题分组**（阶段 0 即：影响"路线方案"／"当季情况"／"时间预算"三组），**只列与本次问题相关或会影响决策的项**。**不写建议的搜索词**——按《阶段0-目的地前期调研提示词》§2，关键词不是给 downloader 的输入，构造关键词是 downloader 自己的职责；
- **不设"新发现的问题"节，不设"可信度与存疑"节**——任何"觉得不对、需要再确认"的点一律写进 §3 缺口，不另开节。

**图卡索引**并入 §2 末尾（路径 + 内容 + 可用于什么），并标注该图是"正文点名·信息在图上"还是"探查发现"；**明确不读的图也要记一行**（如"正文点名的风景照 → 已判为不读"），否则配图或复算环节会把它重新打开一次，白花一遍 token。

## 5. 两个不属于本方案的问题

这两条在实测中撞到，但都不该由 digest 环节承担：

- **重复图（019 = 002 的降采样版）**：`downloads.json` 里 019 的 `source` 是 `background-image`，即页面背景图被当成图片入列了一次，两张图共享同一 asset id、只是 transform 后缀不同（所以 md5 和像素尺寸都不同）。**这是 xhs-downloader 的缺陷，应在下载侧过滤 `background-image`，digest 侧不做去重**（拼图上会自然暴露两格相同，不影响判断）；
- **`downloads.json` 不必进上下文**：14.7 KB 里几乎全是 URL 和 `originalFilename`，信息量 ≈ 0。需要 asset id 时喂给脚本抽几行即可。

## 6. 本笔记整理（实测产出）

本篇整理结果已按 §4 模板落盘：

**`~/Downloads/xhs-digest-笔记整理-九寨沟一日游轻徒步攻略.md`**

三节齐备：

- **§1** 分五小段写全——整体路线（有序走法 + 覆盖范围 + 换乘机制，并指向 `002` 导览图作可视化路线图）／打卡机位／时间与时段／注意事项（取舍）／时效错位；
- **§2** 11 维度全填 + 图卡索引；
- **§3** 缺口按"路线方案／当季情况／时间预算"分组，不写搜索词。

> 相对最初交付形态的三次收敛（均为用户口径）：① 删掉"可信度与存疑""新发现的问题"两节——前者并入缺口，后者不单列；② 缺口收窄为"只列与本次问题相关或会影响决策的"，"吃／住／穿衣／停车／景区外路况未提及"这类留给后续问题的信息保留在 §2，不进缺口；③ §1 从要点摘要改为分小段写全结论本体（原版漏了路线本体、机位、时段、取舍项），并删掉建议的新搜索词一节。

## 7. 复现清单

| 步骤 | 命令/脚本 | 备注 |
|---|---|---|
| 1. 正文 | `Read` `note.json` | **只读正文，先别碰同目录其它文件**；同时记下每张图的处置判据（§2 表） |
| 2. 拼图探查 | `python3 -I sheet.py <images/> /tmp/contact.jpg`（PIL，480 px/格，角标编号） | 单张上限 ≈ 2400×1600；图多就拆几张 |
