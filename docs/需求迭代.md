## R1 ｜chrome-agent：支持关闭 tab

**现状**：命令面（`chrome-agent/SKILL.md` §3）的 `tabs` 组只有 `list | open | claim | activate | navigate`，没有 close。§5 明确要求 *"Leave the user's tabs open unless you were asked to close them"*——目前是刻意的限制，不是遗漏。

**目标**：新增 `chrome-agent tabs close <tab-id>`（含 `--json`），并配一条显式授权规则：只在调用方**明确要求**关闭时才关，且只关 `chrome-agent` 自己开出的、已 `claim` 的标签页。

**验收**

- 关闭成功/失败的判定可机读（关闭不存在的 tab、关闭非本工具 claim 的 tab、关闭用户正在使用的 tab，三种都要有区分度明确的报错）；
- 关闭后 `tabs list` 里不再出现该 tab，daemon 侧的 ref 注册表一并释放；
- SKILL.md §5 的"一律不关"改为"默认不关，被明确要求才关"。

**风险**：误关用户正在用的标签页代价高（可能丢失未提交的表单）；所以 `claim` 记录是关闭的前提，而不是"拿到 id 就能关"。

## R2 ｜chrome-agent：支持发布小红书笔记

**现状**：命令面只有读与下载，没有任何输入类命令；§5 把 **publishing** 明确列进"必须停下来交回用户"的清单。因此《路径图》阶段 3 的「信息缺口追问」功能没有落地手段。

**目标**：新增发布能力（草稿创建 + 提交），供「信息缺口追问」使用——行程细化时某细节多渠道查不到，由智能体发求助笔记向近期到过的人提问，评论作为信息源回收。

**验收**

- 能完成一次"填写标题/正文/配图 → 存草稿"的完整链路，字段落盘为结构化 JSON，便于二次修改重发；
- **提交（真正发布）默认停在草稿，需调用方显式确认**——发布是对外不可撤回动作，不能由智能体自行决定；
- 账号风控可见：发布频率、失败原因（验证码/限流/审核）显式回报，不静默重试。

**依赖**：R1 无依赖关系，但两者都改 `tabs`/页面输入命令面，建议同批做。**与阶段 7.1「笔记撰写」同源**——发布能力做好后，行后沉淀的笔记成文也走同一条链路。

**风险**：自动发布触发平台风控是最主要风险；建议先只做"存草稿 + 人工点发布"，把提交权留在人手上。

## R3 ｜xhs-downloader：评论点赞数采集

**现状**：`comments.json` 的 `comment` / `reply` 结构里**没有点赞数**（`schemas/comments-output.schema.json`，`additionalProperties: false`，`comment` 必填项为 `index / author / text / pinned / byAuthor / replyCount / replies`）。但点赞数在页面上是有的——`parse_comment()` 的注释写明每条评论尾部是"时间地点行 + 点赞数 + 回复按钮"，当前只是把这截 chrome 当作正文结束的标记**丢掉了**（`scripts/comments.py:64-100`）。

**目标**：把点赞数采下来，作为评论的**排序与筛选依据**——高赞评论才是决策信息，长尾评论是噪声。

**验收**

- 结构与既有字段一致：`likeCount`（整数；页面显示"赞"无数字时按 0 或显式未知处理，不允许静默缺失）；
- 解析仍以"时间地点行 + UI tail"为界，`70-200的头` 那类被正文吃掉的回归用例（`comments.py` docstring 记录）不能复发；
- schema 版本号上调，`references/files.md` 与 digest 的读取口径同步。

**风险**：点赞数在页面上可能是缩写（如 `1.2万`），需定死换算与留存口径，否则下游排序不可比。

## R4 ｜xhs-downloader：评论结构精简，降低 token 消耗

**现状**：`replies` 是**层层嵌套**的树（`comment.replies[].replies[]…`，每层重复带 `index / depth / author / pinned / byAuthor / replyTo / replyCount`），xhs-digest 读 `comments.json` 时得把整棵树铺开；评论条数一多，光结构开销就远超正文本身。

**目标**：让"读评论"的 token 成本与**有效信息量**挂钩，而不是与评论总数挂钩。

**方向**（待细化，不外定）：

1. **扁平化**：`replies` 拍平成一维列表 + `parentIndex` 指针，去掉每层重复的字段；
2. **按价值排序**：结合 R3 的点赞数预排序，让 digest 能只读前 N 条就停，而不是全文铺开；
3. **默认截断可声明**：`requested` / `possiblyIncomplete` 已有完整性字段，把"为什么只剩这些"的口径扩到"按点赞截断"，避免被误读成采集失败。

**验收**

- 同一篇笔记的 `comments.json` 体积与 digest 读评论的 token 量可量化下降（改动前后各测一遍，数字写进验收）；
- 完整性判据不退化：`threadEnded` / `possiblyIncomplete` / `noComments` 语义保持不变，截断是"调用方要求的"而非"悄悄发生的"。

## R5 ｜xhs-downloader：部分内容件改为直连请求下载

**现状**：所有内容件都经浏览器取回——媒体走 `chrome-agent page download-images` / `download-media`，产物落在浏览器下载目录的 `chrome-agent/` 下，每次下载都要占一个标签页并驱动页面滚动。

**参考**：同类开源工具（`xiaohongshu_downloader` / XHS-Downloader 一类）绕开浏览器，直接实现小红书 Web 端 `x-s` 签名后调 API 取数据（来源：[解密小红书签名算法：XHS-Downloader 参数生成核心逻辑全解析](https://blog.gitcode.com/015fa86c9a272ca087ea40d23c5a07a9.html)；[2026年小红书搜索笔记逆向数据协议深度解析](https://unifuncs.com/s/HxSm23IG)）。签名本身随前端更新会失效，且已有该方案被反爬拦掉的记录（来源：[Xiaohongshu Anti-Crawling](https://app.dosu.dev/18f08cf8-ce94-4615-8b9a-742a00b3c3ab/documents/91404cba-1067-4bb3-a8af-9bb275530823)）——所以**不是无脑替换，而是先分清哪些件能直连**。

**目标**：媒体件（cover / image / video）优先直连下载，把浏览器标签页留给只有浏览器能做的事（结构件 `note` / `comment` 的数据在页面 SSR 或 XHR 里，脱离浏览器就要复刻签名，维护成本高）。

**验收**（先出一份实测报告，再决定改不改）

- 逐件给出结论：页面已渲染出的 CDN 直链能否用普通 HTTP 取回；需要哪些头（`Referer` / 时效 token / cookie）、链接有效期多长；失败时如何降级回浏览器路径；
- 直连路径与现有 `downloads.json` 记账、`examined` 语义、断点补缺完全兼容——**盘面为准的判据不动**（`references/files.md`）；
- 不改变调用方视角：命令与参数形态保持简单结构化。

**风险**：CDN 链接自带时效签名，`.env` 无、链接过期即作废（`files.md` 已记"CDN 每次重新签名"）；直连省下的浏览器开销若被重试与签名维护吃掉，就不值得做。

## R6 ｜xhs-search / xhs-digest：注入领域文档，提升泛化性

**现状**：两个 skill 的领域知识都**硬编码在 references 里**——xhs-search 的组词公式与搜索条件建议绑定在小红书这一站（`references/query-design.md`），xhs-digest 的图文/视频管线绑定在小红书笔记的版式（`image-pipeline.md` / `video-pipeline.md`）。换个主题（如从川西自驾换到海岛/亲子/冬季雪线），组词习惯、该看的形态词、什么算"有效信息"全都不一样，当前没有注入点。

**目标**：把"不变的流程"与"随领域变的判断"分开——流程留在 SKILL.md，领域知识做成可注入的文档，换领域只换文档。

**方向**

1. 定义**领域文档的契约**（要写什么：领域术语表、可查维度与形态词、信源可信度、该忽略的噪声、时效口径），而不是只准备几篇范文；
2. 至少准备两个领域实例（自驾/徒步为一方，另一领域为对照），用来验证"只换文档、流程不动"；
3. xhs-digest 侧同理：把"什么算有效信息图卡/信息帧"的判断依据外置。

**验收**

- 同一问题在"换领域文档"前后各跑一遍，结论文档的结构与完整性不塌——泛化性靠这个对照验证，不靠感觉；
- 领域文档的 token 成本可控（只在下发子 agent 时读，主 agent 不常驻）。

**风险**：领域文档写过头会变成"新的硬编码"，只是搬了个地方；契约要管住的是**判断口径**，不是穷举词表。

## R7 ｜xhs-search：接入 jev 做决策，降低 token 消耗

**现状**：主循环的每一步判断（构造搜索词、粗筛 J1、对照要求打勾、换词、停机）都跑在主模型上。设计方案已经把这点写进契约——*"契约固定——目前由主模型执行，后续换小模型（jev）时只换执行模型，流程不动"*（`xhs-search-设计方案.md` §4）；也就是说 **R7 是既定路线，不是新主意**，缺的是接线与验证。

**目标**：把机械、低判断量的环节下沉到 jev，主模型只留在真正需要它的地方。

**范围建议**（按收益/风险排序）

| 环节 | 是否下沉 | 理由 |
| --- | --- | --- |
| 粗筛 J1 | ✅ 首选 | 契约已固定为简洁 JSON，输入是标题+摘要+互动数，判断规则明确（从宽把握），最像分类任务 |
| 换词触发判断 | ⚠️ 待评估 | 依赖"已读笔记还缺什么"的上下文，下沉后错误代价高（早停/多跑一轮都是成本） |
| 构造搜索词、打勾、停机 | ❌ 不下沉 | 是主链路决策，错了整轮白跑 |

**验收**

- 下沉环节的输出契约与现在完全一致（同 JSON schema），**只换执行模型**；
- 前后对照：同一问题跑两遍，粗筛 keep 集合的差异率、最终结论文档的完备性各是多少，数字写进验收；
- 主循环日志（`runs/<question_id>.json`）里能看出每步由哪个模型执行。

**风险**：粗筛从宽是刻意的（"误杀代价远大于白下载"）；小模型若偏严，会以"看起来更省 token"的方式悄悄抬高误杀率——所以差异率与误杀抽查必须一起看。

## R8 ｜全链路：引入小红书之外的信息源（官网等）

**现状**：全链路**单源**。xhs-search 的定位就是"在小红书上完成搜索→粗筛→下载→理解→回答的完整闭环"（`xhs-search-设计方案.md` §定位），执行侧只有 xhs-downloader / xhs-digest 两个小红书组件，路由表里没有第三个出口。但《路径图》里对官方源有刚需的字段——1.3 门票预订渠道/价格/优惠政策、宠物政策，1.4 风险提示，2.3 高德路线验证，5.1 天气/路况/政策变化——现在都由小红书**二手内容**回答。仓库内检索"官网/官方/信源"在旅游链路零命中，没有接入点。

**目标**：把官方源作为**一手信源**纳入，且不推翻现有流程。分三步走，后一步以前一步的实测结果为准：

1. **先定口径——哪些必须以官方为准。** 只圈**规则类与时效类事实**：票务价格与优惠、开放时间、预约与限流、封路与管控、宠物/无人机等明确规章。玩法、口碑、机位、排队实况这类**体验类**仍以小红书为主——全都要官方，会让阶段 0/1 瘫掉，且官网本来答不了这些。
2. **关键结论出稿前做官方核查。** 冲突时官方优先并在结论里标注。沿用现有输出契约：结论文档每项标来源，现在从 `noteId` 扩成 `noteId / URL`；缺口声明里记"官方与小红书不一致"为一类，如实并列不调和。
3. **接入点超过两三个之后，再考虑抽象信源层。** 把 xhs-search 的"搜→筛→取→理解"主循环抽成与信源无关的骨架，xhs-search 降为该骨架的一个适配器。**在此之前不做**——一个适配器不构成抽象，提前抽会把小红书特有的组词公式与粗筛规则稀释掉，而那些正是目前质量的主要来源。

**可复用能力**：工具已经齐了——`web-search`（AnySearch/Tavily/Exa）、`web-clipper`（取页面正文）、`chrome-agent`（需要登录或反爬的站点）。缺的是**路由规则与输出契约**，不是工具；所以这一步的成本主要在"什么信息找哪个源"的规则上，不在造轮子。

**验收**

- 阶段 1.3 的票务/宠物政策、5.1 的政策变化，每个字段都能指到官方来源；
- 冲突有明确规则且可追溯：官方与小红书不一致时谁赢、结论里怎么标、缺口声明里怎么记；
- 权威来源可辨识：结论稿里看得出某个字段的权威源是什么，以及该页面的时间；
- 单题成本不显著上升（官方源通常一两个页面即可，不引入新一轮搜索循环）。

**风险**：官方站常是 JS 渲染 + 反爬，且信息散在多个子页（政策在公告栏、票价在购票页、限流在预约页），抓取成本可能高于小红书；另外**官网不等于准确**——过期页面很常见，所以"以官方为准"必须带页面日期，否则会用一个去年的公告推翻今年的实况。景区关闭、高速管制这类只有官方才有的信息，也正是这条需求的价值所在。
