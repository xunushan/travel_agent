# xhs-downloader 设计方案

## 1. 定位

**一个由智能体驱动的小红书下载工具。** 调用方说清楚三件事——**要不要搜索**（搜的话：关键词、筛选项、top-k）、**下载对象**（搜索发现的候选，或直接指定的笔记）、**下载哪些内容件**——智能体据此选择运行哪个代码文件、传什么参数。

- 工具只做机械执行：发现候选、下载内容件、记账（每个内容件下了没有、要不要重下）。**不做任何内容判断**——选词、筛选、留哪篇、什么时候停，都是调用方的事。
- 工具不是零 token：本质是智能体在操作代码完成下载，读输出、决定跑哪条命令都消耗 token，所以命令、参数、输出都保持简单结构化。
- 不自己开浏览器，通过 `chrome-agent` CLI 操作已登录小红书的 Chrome 标签页（`--tab-id` 指定）。

## 2. 功能设计

### 2.1 两个代码文件：discover 与 download

| 代码 | 干什么 | 输入 | 输出 |
| --- | --- | --- | --- |
| **discover** | 搜索并发现候选（**一次一个关键词**） | 关键词、筛选项（可选）、top-k（`--limit`） | 候选清单 JSON：`rank` / `noteId` / `url` / `title` / `publishedAt` / `inLibrary` / `noteDir`，以及**只有已入库的才有**的 `updatedAt` / `type` / `stats`（互动数） |
| **download** | 对指定笔记下载指定内容件 | 笔记（详情页链接或 noteId 列表——可来自 discover 的候选，也可直接指定）＋ 内容件组合（`--part`） | 每篇每个内容件的成功/失败/跳过与路径 |

discover 不开笔记，所以 `updatedAt` / `type` / `stats` 只对盘上已有的笔记有值——它们长在笔记页里，新候选要打开页面才拿得到（已入库的候选从盘上的 `note.json` 读）。`publishedAt` 例外：由 noteId 前 8 位十六进制解出，不用开页面。

`--note-id` 可以只给 id，但**只有索引里存过带 `xsec_token` 的详情页链接时才能重放**：没见过这篇就直接报"先 discover 再下载"，不会按 id 去拼 URL。

**内容件**：`note`（正文全文＋元数据）、`cover`（封面图）、`image`（图集）、`video`（视频）、`comment`（评论树）。相互独立，任意组合。

**典型用法是两者串联**：discover 出候选后，紧接着对候选跑 download——比如调用方说"搜索'甘南小环线'，top-10，下载 note 和 cover"，智能体就跑 discover 再对候选跑 download（note,cover）。也可以只对给定笔记跑 download，比如"这几篇补 image、video、comment"。

筛选项的可选值不写死词表，运行时从页面上读（`discover.py --list-filters`），调用方据此表达筛选意图；选项失效时显式报错，不悄悄退化成无筛选。页面上有哪些维度、怎么挑见 [skills/xhs-downloader/references/flow.md](../skills/xhs-downloader/references/flow.md) 的 §1.1 与 §1.5。

等结果渲染时不能只看"页面上有没有卡片"：`tabs navigate` 是异步的，紧随其后的快照还是被离开的那一页，而 explore 首页与搜索结果页是同一套卡片标记（`section.note-item`），于是"有卡片"会被首页满足，链接却都是 `/explore/` 开头的——一次根本没跑成的搜索会返回一份干净的空清单。所以判据必须是"落在本次关键词的搜索页上，且有卡片"，两个条件同时成立。

### 2.2 落盘结构

`--data-root` 指定本次下载数据的存放路径（默认 `~/Documents/travel_agent`，也可用 `$XHS_DATA_ROOT`；`--db` 可把索引指到别处）：

```javascript
<root>/
  xhs.db                              # notes 表（见 2.3）
  notes/<note_id>_<title>/            # 目录名 = noteId_标题
    note.json                         # note：标题/作者/时间/互动数/标签/正文全文
    cover.<ext>                       # cover：封面图（后缀随源文件，通常是 webp），直接放笔记目录下，不进 images/
    images/                           # image：图集
    videos/                           # video：视频
    comments.json                     # comment：评论树 + 完整性字段
    downloads.json                    # 逐条 URL 的下载状态 + examined（补缺、重试、判"没有"的依据）
```

- 目录名中的标题做文件名安全处理（非法字符换空格、压平空白、按长度截断）；noteId 前缀保证唯一，不怕重名。**目录建一次就不再改名**——`downloads.json` 记的是绝对路径，改名会让整篇的图看起来"文件都不在了"。还没定标题的中断目录（`notes/<noteId>/`）会被合并进标题目录，不留成半篇。
- **`images/` 与 `videos/` 各自只在真的有那种件时才存在**：图文笔记没有 `videos/`；视频笔记没有轮播，页面上那张唯一的图是播放器上的封面帧（CSS `background-image`），归 `cover` 件，所以视频笔记**不建 `images/`**。
- 各内容件自包含、互不依赖。图文笔记的封面就是轮播第一张图，`cover.<ext>` 与 `images/` 里那份独立存放（**重复存一份**，换取两个内容件互不牵扯）。
- `downloads.json` 里的 `examined` 记"页面就这个类型给过答案"，是区分"这篇没有图集/没有视频"和"没人找过"的唯一依据；本轮没读的类型，其条目和 `examined` 由上一轮原样带过来。

### 2.3 状态账：盘面为准，notes 表只记版本键

**"哪个内容件下过没有"一律看盘，不设标志位**——盘上的文件就是唯一事实，不存在表和盘打架的问题：

| 内容件 | "已下载"的盘面判据 |
| --- | --- |
| note | `note.json` 在 |
| cover | `cover.*` 在 |
| image / video | `downloads.json` 里该类型的条目都 `complete` 且文件都还在；`examined` 记了这个类型却一条条目都没有 = **这篇没有这个件**（视频笔记没有图集、图文笔记没有视频），同样算完整 |
| comment | `comments.json` 在且完整（`possiblyIncomplete` 为假） |

`examined` 是"问过"、条目是"有没有"，两个条件缺一不可：只有"问过"没"答过"（读取失败）不能报成"这篇没有这个件"，那会让一次失败永远不再重试。

库里的 notes 表只记**索引与版本键**，回答"这篇见没见过、内容是什么版本"：

```sql
CREATE TABLE notes (
    note_id      TEXT PRIMARY KEY,   -- 24 位十六进制，从链接解出
    url          TEXT,               -- 带 xsec_token 的详情页链接，重放用（只有这里存着它）
    title        TEXT,
    note_dir     TEXT,               -- 笔记目录
    updated_at   TEXT,               -- 编辑时间（SSR lastUpdateTime）
    content_hash TEXT                -- 标题+正文+标签 的 sha256
);
```

判重的口径：`updated_at` **只做正向证据**（只有它比库里的大才算"变了"），两侧任一为空时它什么都证明不了，于是退到 `content_hash` 比较——绝不从一个空字段得出"没变"。`content_hash` 不含互动数（每次都在漂）也不含图片 URL（CDN 每次重新签名）。索引答的是"要不要开页面、重新打开这篇该用哪个链接"；删掉它不丢笔记，只是丢掉链接和版本。

### 2.4 已入库笔记的再下载行为

规则只有两条：

1. **有就不下，没有就下**：调用方请求的每个内容件，盘上有且完整 → 跳过；没有或不完整 → 下载（图片/视频按 `downloads.json` 只补缺的那几条）。
2. **变了就整篇刷新**：打开页面时发现 `updated_at` / `content_hash` 变了 → `note.json` 重写，**盘上已有的件连同本轮请求的件全部重下**，不再属于当前版本的旧文件清理掉。清理只发生在**本轮读过、且这一轮全部下成**的类型上（旧文件可能是那张图唯一的副本）。**「整篇」是有界的**：一篇笔记要么是视频、要么是图集，不可能都有，所以一轮刷新重下的就是封面 + 那一份媒体——绝不把昨天的图和今天的 `note.json` 摆在一起。唯一的例外是评论：**它不属于笔记的内容**，是评论区的、自己会一直变，所以刷新不动它；要新的一轮就 `--part comment --force`（或它还没采过时请求它）。

`note` 例外——**打开页面的第一件事就是重读笔记本身**（标题定目录名、`lastUpdateTime` 定要不要刷新），所以它只要开页面就一定是这一轮写下来的。被顺带刷新（本轮没请求但盘上有）的件会出现在报告的 `parts` 里，下失败也照 `FAILED` 报——刷新的意义就是让目录里只有一版。

什么时候会打开页面（也只有打开页面才能发现"变了"）：**有缺口件要下载时顺带核验**；或**调用方显式要求"检查更新"**（`--check-update`）。请求的件盘上都有、且没让检查更新 → 整篇跳过，连页面都不开。

`--force` 与之正交，而且更窄：它只管**本轮请求的件**（无视盘上有没有，别的件不动），所以"只重采评论"就是 `--part comment --force`。

| 例子 | 行为 |
| --- | --- |
| A 已下过 note+cover+image；又要"下载 A 的 note、image" | 盘上都有 → 整篇跳过，不开页面，返回已有路径 |
| A 只下过 note+cover；要"补 video、comment" | 有缺口件 → 打开 A 顺带核验：没变 → 只下 video 和 comment（`note.json` 每开一次页面都会重写） |
| 补 A 的 video 时打开页面，发现作者 10-08 编辑过 | 变了 → `note.json` 重写，盘上已有的 cover / 图集连同本次请求的 video 一起重下，旧图删掉；报告里多出 cover=已下载、image=已下载 |
| "检查一下 A 有没有更新" | `--check-update`：打开页面核验，没变 → 什么都不动；变了 → 按规则 2 整篇刷新 |
| "刷新 A 的评论" | `--part comment --force`：只管评论，无视盘上已有的 comments.json 重新采集覆盖（评论随时在涨，和笔记有没有编辑过无关） |
| 搜"甘南小环线" top-10，其中 3 篇上周搜别的词时已入库 | 在库的 3 篇不重开页面，用盘上 note.json 生成清单条目（标注"在库"），只打开其余 7 篇；要新鲜数据就说"检查更新" |

一句话：**"有就不下"是默认；"变了"或"调用方明确要求"才重下，变了就把这篇整个刷新到当前版本。**

### 2.5 输出与报错

- discover 末尾打汇总行：候选 n 条 / 在库 x / 新发现 y；清单 JSON 走 stdout，进度与摘要走 stderr（`> candidates.json` 拿到的就是干净 JSON）。
- download 对每篇给出 `action`：`new`（从没存过）/ `fill`（存过、没变，这一轮读了请求的件——补缺的或 `--force` 重读的）/ `refresh`（变了，整篇重下）/ `check`（开页面核验了、没变，除开页面必写的 `note.json` 外没动任何件）/ `skip`（件都在，连页面都没开）；`parts` 逐件报四态：`已下载` / `已存在` / `无此件` / `未完成`。`refresh` 的 `parts` 会多出本轮没请求、但盘上有因而被顺带刷新的件——它们确实重下了，不静默。
- 一切失败显式报告——**不把「没下成」含糊成「没有」**：有件没下成就是 `FAILED` 并以非 0 退出，`reason` 点名是哪件；页面的否定回答才报 `无此件`，且不落任何文件。`--json` 时报告走 stdout，进度一律 stderr。
