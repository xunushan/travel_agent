# 阶段 0：主题前期调研（skill 草案）

> 本文按 skill 的结构编写，但还不是 SKILL.md——流程已经清晰，个别环节的工具选型见 §8 方案建议（待用户拍板）。定型后再拆分为 SKILL.md + references/。
> 配套文档：《xhs-downloader 设计方案》（§2 的分工以其为准）、《阶段0-时效性筛选结论》（筛选建议的参考依据之一）、《HTML海报生成方案调研》（§8 输出方案的选型依据）。

## 1. 定位

**围绕用户的出行意图，提供候选景点列表与常见路线方案**——附当季情况与时间预算，让用户有足够信息决定"去哪些景点、走哪条线"。

- **输入**：用户意图（目的地/主题 + 计划出行时间，其他信息通过澄清补齐）
- **输出**：《【主题】游览总览》（HTML）+ 用户圈选后的景点清单（阶段 1 的输入）
- **做**：澄清意图 → 拆问题 → 逐题调 xhs-downloader 拿笔记 → 汇总结论 → 配图 → 生成总览 → 处理用户反馈
- **不做**：
- 搜索、单篇笔记的 keep/drop 判断、下载——**xhs-downloader 的职责**；
- 单景点的口碑、避雷、玩法细节——**阶段 1 的任务**；
- 实时路况/人流/天气的临行校准——阶段 3/5 的任务（本阶段只回答"这个季节通常怎么样"）。

## 2. 与 xhs-downloader 的分工与调用

downloader 的接口：**一个问题进，一批 keep 笔记出**（落盘 `notes/<noteId>/`：正文、图片、视频、评论）。

**调用形态**：每题派一个子 agent 调 downloader。downloader 不知道也不关心问题从哪来、一共几个问题。

阶段 0 给 downloader 的输入只有三样：

| 输入 | 必需 | 说明 |
| --- | --- | --- |
| **问题** | 是 | 判断的单位，一次一题 |
| **判定标准** | 否 | "怎么算这篇笔记能回答这个问题"，见 §4 每题的配置；给了就按它判，防止退化成"主题相关就留" |
| **筛选建议** | 否 | 见 §4 每题的配置；只是提示，downloader 用 `discover.py --list-filters` 读页面上的真实选项自己落成筛选 |

**关键词不是输入**——构造关键词、换词、调筛选是 downloader 的核心能力，阶段 0 不干预。

**素材库**：所有下载的笔记都在 `notes/` 目录，本阶段配图、阶段 1 深度调研均从这里取，不重复下载。

## 3. 与用户的交互

### 3.1 开始前：澄清式提问（按需，非固定表单）

不给用户看问题清单。而是**根据目标和用户已表达的意图，判断缺什么信息，有针对性地提澄清问题**：

- 意图已明确（如"10 月中旬去甘南"）→ 直接开干，不为问而问；
- 有缺口才问，且只问影响调研方向和输出的关键项，例如：
- 主题范围模糊（"想去川西" → 秋色？雪山？人文？）；
- 出行时间缺失（影响当季情况的判断）；
- 时间预算缺失（影响路线方案的筛选——3 天小环线还是 7 天大环线）；
- 显著偏好（如"不想太累""想露营"——用于调整判定标准，不展开约束）。

### 3.2 产出后：反馈处理（必需）

用户看完总览后的反馈分三类，分别处理：

| 反馈类型 | 处理流程 |
| --- | --- |
| **圈选**（正常路径） | 记录每个景点的 待调研/排除 标记 → 输出阶段 1 任务清单 |
| **补充/纠偏**（"想看看 XX 方向""这个路线天数不对"） | 把反馈拆成新的问题 → 调 downloader 补充调研 → 更新总览对应章节 → 再次请用户确认 |
| **方向调整**（"其实更想看雪山，不只是秋色"） | 回到 §3.1 澄清新方向，按需增补/替换问题后继续；已下载的笔记留在素材库可复用。**注意**：换一个目的地（如"改去新疆"）不属于反馈，而是规划一个新行程，应另走一遍完整流程 |

## 4. 问题设计（核心）

### 4.1 拆题原则

- 标准配置只有 **3 个问题**，问"是什么/怎么样/要多久"——但这是**骨架不是定稿**，skill 必须根据用户提供的信息动态设计出最合适的问题；
- "路线之间怎么对比""景点卖点是什么"这类问题**不单独设题**——Q1 的笔记拿回来后，在汇总环节内部对比、提炼即可；
- 口碑、避雷不进本阶段——那是选定景点后阶段 1 的事；
- 一次一题；某题搜出来太杂，就拆得更小（如按路线逐条查）。

**动态设计问题的四个杠杆**（根据用户已提供的信息调整）：

| 杠杆 | 怎么调 | 例子 |
| --- | --- | --- |
| **题量** | 意图中已明确的维度不重复设题 | 用户说"只有 3 天"→ Q3 不单列，改为 Q1 判定标准加"3 天以内短线"侧重；主题已是具体路线（如"格聂南线"）→ Q1 收缩为"这条线的节点与天数"一题 |
| **措辞** | 把主题语义写进问题，不泛泛问 | 主题是"秋色"→ Q2 问"秋色进度与峰值期"，而不是"景色怎么样" |
| **侧重** | 显著偏好不改问题，改**判定标准** | "带狗"→ Q1 判定标准加"带宠物信息的笔记优先"；不新增"宠物题"（细节归阶段 1） |
| **增题** | 命中触发条件才加 | 偏远目的地 → 大交通题；高原主题 → 高反概况题（见 §4.3） |

### 4.2 标准问题清单

以"10 月中旬去甘南"为示例，【目的地】【出行时间】为占位符：

| # | 问题（模板） | 判定标准（给 downloader） | 筛选建议（给 downloader） |
| --- | --- | --- | --- |
| Q1 | 【目的地】有哪些常见的环线/路线方案？各包含哪些推荐景点、节点顺序和大致天数？ | 正文要有路线结构信息：节点顺序、天数、里程至少占其一；只有风景照、无路线信息的 drop | 排序依据=最多收藏，时间不限（路线结构弱时效）；优先正文带数字（天数/里程）的笔记 |
| Q2 | 【出行时间】这个时间点去【目的地】，景色、天气、路况怎么样？ | 要有对应该时间段的描述：当季看点（如秋色进度）、气温/穿衣、路况概况（如哪些路段难走、是否季节性封路）；年份不明的 drop | 分两层：往年同季给"典型情况"——关键词带月份（如"甘南 10月"）+ 时间不限；当年实况做校准——"最新+一周内"。规划期以典型情况为主，临行校准归阶段 5 |
| Q3 | 走完【目的地】的这些路线，一般需要多少时间？ | 要有明确的时间/天数表述（总长、日均车程、节奏快慢）；泛泛而谈的 drop | 排序依据=最多收藏，时间不限（弱时效） |

**说明**：

- 每题支撑结论的笔记 ≤10 篇（经验上 5 篇够）；单题累计读取 20 篇硬停（由 downloader 执行）；
- 提问时带着输出意识：Q1 的答案对应总览的"路线方案 + 景点集合"，Q2 对应"当季情况"，Q3 对应"时间预算"。

### 4.3 可选增题（按主题判断，默认不加）

| 候选问题 | 什么时候加 |
| --- | --- |
| 从哪里进出【目的地】最方便？大交通/必经枢纽？ | 目的地偏远、入口多样时（如新疆、西藏） |
| 【目的地】的海拔与高反概况？ | 高原主题（川西、甘南、西藏等）——只需概况，细节归阶段 1 风险组 |

### 4.4 筛选建议的依据与经验

- 路线/时长类是弱时效（一年内基本不变），用"最多收藏+时间不限"；性价比高的路线笔记普遍发布于 1-4 个月前，"最新+一周内"会精确杀掉它们；
- 当季情况是中时效：同地每年差 1-2 周，所以"往年同季给典型、当年实况给落点"；
- 发布时间筛选只有四档（不限/一天内/一周内/半年内），"近一两个月"只能"不限+自己看笔记时间"近似；
- 判断一篇笔记的时效，看 `publishedAt`/`updatedAt` 中较晚的那个；结论里要标注笔记年份——用 2025 年的情况回答 2026 年的行程是错的。

## 5. 工作流程

```javascript
0. 澄清：按 §3.1 判断是否需要向用户提问，补齐意图
1. 拆题：按 §4 生成问题清单（默认 3 题，按主题判断可选增题）
2. 逐题执行：每题派一个子 agent 调 downloader
   （输入：问题 + 判定标准 + 筛选建议；一题多轮、换词、20 篇硬停均由 downloader 内部处理）
   → 子 agent 返回：该题的 keep 笔记清单 + 每篇 keep 理由
3. 汇总：交叉印证各题答案；合并去重景点；
   内部完成路线对比（天数/难度/景色侧重）与景点卖点提炼（一句话定位）；
   结论有分歧时如实并列，不擅自调和；
   汇总层面发现明显缺口（如某条路线完全没有景点信息）→ 补一个拆小的新问题回第 2 步
4. 配图（素材全部来自 notes/ 库，不另搜）：
   - 路线图：优先收录笔记中现成的高清线路图/海报，注明来源；没有合适的才自制文字版结构图
   - 景点美照：每景点 2-3 张，从 keep 笔记的 images/ 里挑，记录来源 noteId
   - 视频型笔记的处理见 §8.1
5. 生成《【主题】游览总览》HTML（结构见 §6，生成方式见 §8.2）
6. 用户反馈：按 §3.2 的三类反馈处理；圈选完成 → 输出阶段 1 任务清单
```

## 6. 输出要求

《【主题】游览总览》HTML 一份，自上而下：

1. **主题与一句话结论**：如"10 月中旬甘南秋色正盛，推荐 4-5 天小环线"；
2. **当季情况**：景色看点、天气气温、路况概况（Q2 的答案，标注信息年份）；
3. **常见路线方案**：每条路线给出 节点顺序 / 大致天数 / 一句话特点（Q1+Q3 的答案，汇总时内部对比）；优先收录笔记中现成的高清线路图（注明来源）；
4. **候选景点集合**：按路线分组，每景点给出 名称 / 一句话定位 / 2-3 张美照；
5. **笔记来源清单**：标题 + 链接 + noteId，便于溯源和复用素材。

格式：HTML。图片引用本地 `notes/` 路径（笔记图片有防盗链，不直接外链）。

## 7. 完成标准

- 用户看完能回答：有哪些常见路线方案、各含哪些景点、这个季节去怎么样、走完需要多少天；
- 用户能看着美照，直接圈选出进入阶段 1 深度调研的景点；
- 总览中每个结论都能溯源到 `notes/` 里的具体笔记。

## 8. 方案建议（待用户拍板）

### 8.1 视频型笔记的理解（汇总环节）

概括类笔记中视频占比不低，且视频笔记正文往往很薄。建议**分层处理，先用最便宜的**：

| 档位 | 做法 | 成本 | 什么时候用 |
| --- | --- | --- | --- |
| L1 近似判断（**默认**） | 封面图 + 标题 + 评论（高赞评论常含路线信息） | 极低 | 阶段 0 的大多数情况——概括类问题信息密度要求不高 |
| L2 轻量视频理解 | ffmpeg 抽关键帧（每 2-5 秒一帧）→ 图像理解；有解说的话 ASR 转字幕 → 文本理解 | 中 | 某题闭合不了、且候选以视频为主时升级 |
| L3 完整视频理解 API | 直接送视频给多模态模型 | 高 | 兜底，阶段 0 基本用不上，阶段 1 玩法调研可能更需要 |

**调研结论补充**（详见《视频理解方案调研.md》）：

- 工具链：`ffmpeg/opencv` 抽帧 + Whisper（本地 ASR，免费但慢）或云 ASR + **与主 Agent 同生态的多模态视觉模型**（不单开技术栈）+ PaddleOCR（文字密集帧兜底）；
- **成本控制的关键是分级调用**：先跑 ASR 和 OCR 拿文字信息，纯文字能回答的就不调多模态模型；确需理解画面时才把少量关键帧送视觉模型——成本大头是多模态 API 调用，不是抽帧；
- 延迟瓶颈在 ASR（一小时视频本地转写需数分钟级），本阶段离线批处理可接受。

### 8.2 输出生成（HTML 与海报）

基于《HTML海报生成方案调研》的结论，建议：

1. **生成方式**：LLM 生成单文件 HTML（内联 CSS、图片用本地路径）；

- 先用**模板填充模式**：预置一个"游览总览"HTML 模板，LLM 只填坑位（结论/路线/景点/图），保证下限；
- 积累几套模板后再开放自由生成 + 人工反馈迭代，拉高上限；
- 版式与渲染管线直接借鉴 **guizang-social-card-skill**（深入调研见《HTML海报生成方案调研.md》§七）：它的"版式骨架 + 主题预设"思路、`render.mjs` 渲染脚本、Playwright validator 校验脚本都可直接抄；Editorial（杂志风）契合旅行内容。注意三点：① 它是 **AGPL-3.0** 协议，自用没问题，产品化分发需评估开源义务；② 它的模板是卡片尺寸（3:4/21:9），总览长页面需自建模板，只借设计语言和管线；③ 取图环节要改造为从 `notes/` 素材库取图；

2. **海报导出**：需要长图时，Playwright 无头浏览器全页截图（`deviceScaleFactor: 2~3` 保证清晰度；截图前等字体/图片渲染完成）；HTML 与海报同源，一份代码两种消费；
3. **质量自检**：图片全部本地化、中文字体显式指定、无文字溢出、无图片占位框。
