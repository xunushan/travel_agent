# xhs-search 设计方案

> **定位：给一个问题和要求，在小红书上完成"搜索 → 粗筛 → 下载 → 理解 → 回答"的完整闭环。**
> 依赖 xhs-downloader（discover＋download）、xhs-digest（单篇理解）。
> 问题的粒度由调用方把握——不会把很粗的问题扔进来；本组件也不拆问题、不做跨问题汇总、不与用户交互。

## 1. 接口

**输入**（仅两样）：

| 输入 | 说明 |
| --- | --- |
| **问题** | 判断与回答的单位，一次一题 |
| **要求** | 答案要覆盖的维度/结构（如"路线列表：名称/节点顺序/天数/特点"），可含怎么算"能回答"的判定口径——闭合判断的对照表 |

搜索词、搜索条件（排序/时间筛选）、top-k、读几篇——全部由 xhs-search 自己决定，不是输入。

**输出**（仅两样，面向问题与要求；digest 存档、run 日志都是中间数据，不是输出）：

1. **结论文档**（结构见 §5）；
2. **缺口声明**（结构见 §5；仅当多轮尝试后仍有未覆盖项时存在）。

## 2. 流程

```javascript
问题 + 要求
 │
 ▼
构造搜索词 + 搜索条件 + top-k（主 agent 决策，§3）
 │
 ▼
派子 agent 执行 discover＋download top-k（内容件 note,cover）→ 返回候选清单
 │                                              │
 │ 换词（§4）                                   ▼
 │                              粗筛（派子 agent，§4）：
 │                              读标题+摘要（拿不准再看封面）
 │                              → 简洁 JSON：keep 列表（有序）
 │                                              │ keep
 │                                              ▼
 │                              按序逐篇派子 agent：
 │                              download 完整内容件 → digest 理解
 │                                              │
 │                                              ▼
 │                              对照"要求"逐项打勾（主 agent）：
 │                              ├─ 全覆盖 → 输出结论文档（同点异称在此时归并，§5）
 │                              ├─ 本轮 keep 还有没读的 → 继续读下一篇
 │                              └─ keep 读完仍未覆盖 ──┘
 └──────────────────────────────┘
 6 轮用尽仍未覆盖 → 输出结论文档 + 缺口声明
```

**主从分工**：主 agent 只做决策——构造搜索词与条件、对照要求打勾、换词、停机、写输出；一切执行（搜索下载、粗筛、逐篇下载＋理解）全部派子 agent，回主 agent 的只是各步的简洁结论（候选清单、keep JSON、digest 报告），原始页面内容和长文不进主上下文。

## 3. 构造搜索词与搜索条件

### 3.1 搜索词

- **组词公式：对象 ＋ 信息形态词**。小红书搜索页提供的 tag 可直接用来组词：导航定位、门票价格、路线图、分布图、实况、照片、最佳时间、看日出、攻略、自驾、海拔（如"扎尕那 分布图""扎尕那 门票价格"）；tag 也可当作"这个问题有哪些可查维度"的提示；
- **泛词低效、形态词高效**："扎尕那旅游攻略"这类词同质化严重且夹广告，避免单用；
- **一次一词**：一轮搜索只用一个关键词，多词合并会丢候选；
- **top-k 默认 8**：一个关键词下有效候选通常 3–5 篇，候选少是常态，换词比深挖重要；
- **换词的依据**：已读笔记回答了什么/还缺什么（对照要求）；已读笔记里长出的新词（新地名、新形态词——digest 报告的缺口和素材里常有）。

### 3.2 搜索条件建议（什么时候选什么）

| 问题类型 | 排序 | 时间筛选 |
| --- | --- | --- |
| 路线/结构类（路线方案、分布、时长） | 最多收藏 | 不限——好的路线笔记普遍发布 1–4 个月前，限时间会杀掉它们 |
| 口碑/评价类 | 最多收藏 | 不限，同题多篇时挑 updatedAt 近的 |
| 观赏窗口类（秋色进度、花期） | 最多收藏 | 不限，搜索词带月份（如"10月"）；若问的是"今年秋色在什么时间段"这类实时进度，改最新＋一周内 |
| 路况/人流类 | 最新 | 一周内 |
| 天气类 | 最新 | 一天内 |

以上均为**建议默认值**，xhs-search 可按实际情况灵活调整（如条件太严导致候选稀少就放宽）。另：时间筛选只有四档（不限/一天内/一周内/半年内）；判断笔记时效看 publishedAt/updatedAt 较晚者，结论标注年份；完整选项清单见 downloader 的 `references/filters.md`。

## 4. 粗筛与换词

**粗筛（J1）**：派子 agent 一次批量判断一轮候选，输入＝问题＋要求＋候选清单（标题＋200字摘要＋互动数＋publishedAt＋类型），先扫标题和摘要，**拿不准的再看封面**（读图约 1–1.5k token，能凭文本判的不看）。输出简洁 JSON：

```json
[{"id": "noteId", "keep": 1, "pri": 1, "why": "≤10字"}]
```

规则：从宽把握——只要主题沾边、可能含所需信息就 keep，只 drop 明显无关、广告、地区不符；拿不准一律 keep 压低优先级（误杀代价远大于白下载）；pri 即阅读顺序。契约固定——目前由主模型执行，后续换小模型（jev）时只换执行模型，流程不动。

**换词**：粗筛后无一可用（keep 为空），或连续 ~3 篇读完无增量，或本轮 keep 读完仍对照要求有缺项 → 按 §3.1 的依据重构搜索词（可同时放宽搜索条件）再来一轮。

## 5. 输出契约

### 结论文档

```text
# <问题>
## 结论      ← 严格按"要求"的结构逐项组织；每项结论写全本体、标注来源 noteId；
                分歧如实并列，不擅自调和；涉时效的结论标注信息年份；
                名单类结论的同点异称在输出时处理：基于已读内容能对齐的归并
                （同点只出现一次，括号附各异称及其来源路径/noteId）；
                不能确定的进缺口声明，别名不为它发起补搜
## 关键素材   ← 与结论相关的图卡/关键帧/美照：本地路径 + 一句话
```

### 缺口声明

**xhs-search 必须按"要求"尽力完整回答**；缺口是例外不是常态——收两类：①**多轮尝试（直至停机）后仍无法获取**的项；②基于已读内容**仍无法证实的疑似同点异称**（须附判断为别名的证据及引用路径）。缺口的界定与后续处置（换个问题再调、放弃该项、人工核实别名）由调用方决定。

```json
{
  "gaps": [
    {"item": "要求中未覆盖的项", "tried": "试过的搜索词", "why": "判断无法获取的理由"},
    {"item": "疑似别名：A / B", "tried": "—（别名不触发补搜）", "why": "未能证实为同一点",
     "evidence": ["疑似依据一句话＋引用路径/noteId"]}
  ]
}
```

## 6. 停机准则

满足任一即停：

| 准则 | 阈值 | 停后动作 |
| --- | --- | --- |
| 闭合 | 对照"要求"逐项有带来源的结论支撑 | 输出结论文档（剩余候选不再读） |
| 轮次上限 | **最多 6 轮搜索**——有些内容小红书上就是没有答案 | 未覆盖项写入缺口声明，照常输出 |
| 深度上限 | 单题完整理解 ~10 篇软上限、20 篇硬停 | 同上 |

## 7. 运行日志

每次运行落一份 JSON（`runs/<question_id>.json`，question_id＝问题归一化后 sha1 前 8 位），结构固定：

```json
{
  "question": "...", "requirements": "...",
  "rounds": [
    {"keyword": "...", "filters": "...",
     "candidates": ["noteId"],
     "screen": [{"id": "...", "keep": 1, "pri": 1, "why": "..."}]}
  ],
  "reads": [{"id": "noteId", "verdict": "used | duplicate | no-increment"}],
  "stop": {"reason": "closed | rounds-cap | reads-cap", "rounds": 0, "reads": 0},
  "sources": ["noteId"],
  "gaps": []
}
```

## 8. Skill 实现

本 skill **不带任何代码文件**：执行全靠派子 agent 调 xhs-downloader / xhs-digest 两个已知 skill，主 agent 只做决策和写 JSON。目录：

```javascript
xhs-search/
├── SKILL.md                    ← 主循环＋换词与停机准则＋路由表
└── references/
    ├── query-design.md         ← 构造搜索词与搜索条件（本方案 §3 全文）
    ├── screening.md            ← 粗筛子 agent：输入、契约、从宽规则（§4 粗筛部分）
    └── output-formats.md       ← 结论文档、缺口声明、run 日志结构（§5、§7）
```

**只拆三份 references**：query-design（组词/条件细节多，且只在每轮开头读一次）、screening（随粗筛子 agent 任务书下发，主 agent 自己不用读）、output-formats（只在收尾写输出时读一次）。**换词与停机不拆**——就三条触发＋三行表，是主 agent 每次打勾都要对照的决策逻辑，直接写在 SKILL.md 里，为这点内容多读一次文件不值。

**SKILL.md 要带着可执行的流程走**，不是空骨架：

```markdown
---
name: xhs-search
description: 给一个问题和要求，在小红书上完成"搜索→粗筛→下载→理解→回答"的闭环。
  输入仅问题+要求；输出仅结论文档+缺口声明。主 agent 只做决策，执行全派子 agent。
---

主循环（每轮）：
1. 构造搜索词＋搜索条件＋top-k（规则见 references/query-design.md）
2. 派子 agent 调 xhs-downloader（discover＋download top-k，内容件 note,cover），拿回候选清单
3. 派子 agent 粗筛（契约见 references/screening.md，随任务书下发），拿回 keep JSON
4. 按 keep 顺序逐篇派子 agent：xhs-downloader 下载完整内容件 → xhs-digest 理解，拿回报告
5. 每拿回一篇报告，对照"要求"逐项打勾，三选一：
   - 全覆盖 → 走第 6 步
   - 本轮 keep 还有没读的 → 回第 4 步读下一篇
   - keep 读完仍有缺项 → 换词回第 1 步
6. 写结论文档＋落 run 日志（格式见 references/output-formats.md）：
   同点异称在此时处理——能对齐的归并并标注各别名来源路径；不能确定的进缺口声明，
   附疑似证据与引用路径。别名全程不触发搜索，不影响主链路。

换词触发（满足任一）：粗筛 keep 为空；连续 ~3 篇读完无增量；本轮 keep 读完仍有缺项。
停机准则（满足任一）：要求全覆盖（闭合，剩余候选不再读）；搜索满 6 轮（缺项写入缺口声明）；
完整理解满 ~10 篇（软上限）/20 篇（硬停，同上）。

xhs-downloader、xhs-digest 是已知 skill，直接调用，不经路由。
```

路由原则：**本 skill 自有的重判断才路由**（组词细节、粗筛契约、输出模板——内容多或只服务子 agent）；**轻决策直接写在 SKILL.md**（换词、停机）；**调已知 skill 不路由**（下载、单篇理解，主 agent 知道要调就直接调）。
